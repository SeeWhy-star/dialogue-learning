# 笔记结构与表达示例

仅在需要详细版式示例或整理成跨会话文档时参考本文件。普通聊天笔记以 `SKILL.md` 的默认规则为准。示例说明表达方式，不要求其他话题复制支付术语、四个主题或固定栏目。

## 先确定完整回顾范围

- “这次／本轮／这段对话”默认指当前选中的单一聊天线程；“那次旧聊天”指用户明确指定的线程或文件。只使用平台直接提供的该线程消息和本线程明确附带的文件，不搜索本机会话数据库、其他聊天、项目仓库、Git 或带教资料。
- 不只总结最近几轮。若平台提供当前线程的完整历史，可据此回顾；若只提供部分内容，简短说明缺失范围。不要为补齐而扫描本机记录或拼接相邻会话。
- 长对话可以按主题整理，但无需为了证明覆盖完整而生成逐段审计清单。用户指出漏项时，先在当前线程材料中定位。

## 开头：回到当时

标题概括实际主题。一段连起用户目标、学习样本或工作主线、重要讨论与最后进展。例如：

> **回到当时：**你已经做过支付渠道接入，但希望把零散代码连成完整业务流程，同时判断这些经历怎样支持 Java 后端和区块链方向求职。我们选择 Asteripay 作为学习样本，重点讨论了请求模板、响应解析、跳转页面、订单状态和回调。最后推进到了独立 Demo 的规划与实习简历整理；这段对话中没有完成 Demo 的运行验证。

需要覆盖更广背景时补一句整段还讨论什么，不再另写一段重复概括。长对话可在末尾列出正文未展开但值得回看的旁支。仅当平台实际只提供部分内容时，才简短说明范围；不要用工具说明占据回忆入口。

## 正文：直接回答，沿理解顺序展开

问题标题之后立即给明确解释或当时结果，再讲用户为何混淆、具体例子或操作过程、关键更正与留下的方法。用自然段连接，只有比较或顺序更清楚时用表格、列表、流程。不要机械铺满现象、证据、判断、关联、掌握等栏目。

### 表格既易读，也帮助定位代码

概念比较写“主要负责什么”，不要把内容改成一串待回答问题：

| 层次 | 主要负责什么 | 与当时项目的关系 |
|---|---|---|
| 支付平台 | 商户订单、渠道路由、退款、回调、状态同步 | 公司项目的核心 |
| 链上支付应用 | 查询交易、核对资产与收款地址、判断确认情况、关联订单 | 希望通过个人 Demo 补上的能力 |
| 区块链底层 | 节点、交易验证、区块、共识等 | 当时代码未证明涉及这类开发 |

代码走读要保留具体文件和输入输出，不为简洁删掉定位信息：

| 内容／文件 | 输入或来源 | 作用与输出 | 主要使用者 |
|---|---|---|---|
| `payment.vm` | Java 准备的内部字段 | 渲染渠道请求 JSON | 渠道 API |
| `AsteripayPayment.groovy` | 响应字符串 `message` | 解析为内部 `WooshgwMessage` | Java 渠道业务代码 |

当聊天中已有具体类、方法或步骤时，必要时再附一条调用链，帮助用户回到代码继续读，例如：

```text
业务入口 → 业务策略 → 请求工厂／策略 → 模板或脚本 → HTTP 调用 → 响应解析
```

保留聊天里出现且有助于继续学习的名字；不要为填满目录搜项目文件。引用了聊天中的代码片段时可说明它支持什么结论；推断出的调用关系就近注明待确认。表格单元、流程图和正文保持一致的确定程度。

表格后可保留关键纠错的集中强调，帮助记住：

- **Velocity 请求模板：内部参数 → 渠道请求文本。**
- **这个 Groovy 响应解析器：渠道响应文本 → 内部消息对象。**

表格负责定位，加粗负责记忆。重复强调关键区别有教学价值，但不要再把同一表复制到环境快照和概念速查中。

### 排障保留为什么，而不只是成功命令

例如：服务器访问公网 IP 成功，但访问域名报 `Could not resolve host`，所以转向 DNS 检查。修改 DNS 后访问恢复，说明当时存在解析故障；原 DNS 的失败原因和永久配置仍待确认。

必要时使用“检查／实际结果／支持的判断”表格，只留改变诊断方向的证据。命令注明本机或服务器、PowerShell 或 Linux。重要失败需保留；重复重试、工具补丁失败、提交过程按学习价值取舍。

### 限定与来源贴近结论

流程图只画有依据的路径；推测节点就地写“待核实”。来源在主题末尾简短附注，如：

> *来源：用户贴出的 `parse(String message)` 与请求模板，以及“先把 HTML 放入 Redis”这轮讨论。*

补充解释和例子不得说成历史实验。新识别的风险仅列待核查，不在回顾任务里启动审计。不要用“并非全部证明／尚未重新验证”反复打断正文。

用户和助手在聊天中说过什么，是可记录的历史事实；它本身不等于相关代码已验证。保留重要讨论并归属给当时的发言者，只有在会影响学习结论时才简短标注“代码未核实”。整理任务不需要为了重新验证而搜索聊天外资料。

## 接续与查找

“下次从哪里继续”按价值排序，写具体行动和必要的完成标准，项数按材料决定。区分历史遗留、整理时新疑点、未来兴趣，不让所有候选问题变成同等紧急任务。

末尾“其他讨论的查找入口”覆盖正文未展开但仍有意义的内容，通常用两列。开头主题入口帮助读者选择正文主线，末尾目录帮助定位零散旁支，不能用前者取代后者。正文聚焦不代表从覆盖范围里删除旁支：例如求职回顾可简短列出原对话确实推荐过的开源项目名称和用途；注明这是建议，不是已完成的贡献，并按来源规则核对具体名称。

| 讨论 | 内容与定位线索 |
|---|---|
| 配置与服务调用 | Nacos、Dubbo；用户明确指出的盲区 |
| 开源方向 | 历史推荐及用途；无实际贡献记录时简短注明 |
| 简历展示 | 技术栈取舍、关键加粗；具体产出或原提问 |

不重复正文完整结论。复杂目录可以增加真实文件链接或状态，不默认加入多套编号、来源列和掌握评分。

讨论笔记格式、skill 设计或整理体验的元对话，通常不属于被回顾的技术主题。按用户指定范围处理；若用户要求总结整段对话，可以把它独立列为“学习方法／笔记设计”，不要混进技术问题正文。

## 保存与增量维护

内容少时一份 Markdown 即可。跨会话积累按需采用：

```text
knowledge/
  index.md
  sessions/
    session-001.md
  topics/
    payment-channel-learning.md
```

- `index.md` 汇总主题、范围和真实文件链接，不复制各篇全文。
- `sessions/` 保留本次笔记与来源；`topics/` 汇总反复出现、值得跨会话复用的知识。
- 已有稳定标识和锚点应保留，新增标识不与其他会话冲突；标识服务存储和链接，不主导正文阅读。
- 合并时保留环境、适用条件和新证据；旧结论已被纠正则标明，并指向新解释。冲突未解决不能静默选一方。
- 理解程度仅依据实际解释或独立操作。复习请求才出题、等待回答并记录反馈，默认整理不设测验。
- 原始聊天导出、全局记忆、项目规则和外部发布不包含在普通笔记保存授权中。
